The question

Not "is it as good as Claude?" — but what fraction moves local, at what latency and energy, and where does it break?

Why screenshots lie

A model that draws a nice pelican or a pretty solar system tells you nothing about whether the physics is right. Viral prompts are also memorised: we changed every parameter of the classic "balls in a spinning polygon" prompt.

Two rules

  • Correctness is binary and checked by code — no 1–5 rubrics.
  • Clean pass = verifier passes and the agent finished before the 50-minute timeout.
  • Every claim → a line in results.csv + a raw log.

What we measure

  • pass@1 over K = 3 runs
  • wall-clock time per run
  • SoC package power (AMD PPT sensor)
  • API-equivalent cost (Claude side)

Hardware & software

  • AMD Ryzen AI MAX+ 395, Radeon 8060S, 32 threads, 128 GB unified memory (~123 GiB usable)
  • Ollama 0.33.3 · qwen3.8 27B, Q4_K_M, context 262 144
  • Claude Opus 5 via Claude Code (subscription)
  • Harnesses: Claude Code, pi, pi + SoL-Pi, prime-agent

Rules (PROTOCOL.md, 17 Sep)

  • K = 3 runs per cell · fresh fixture per run · timeout 3000 s
  • Same prompt, verbatim, for every model and harness
  • Verifiers validated both ways (make check-reference)

Deviations we found — and disclose

  • Effort: protocol pinned medium; Claude Code sends effort: "high" unless --effort is passed (captured on a fake server). The original grid ran at high. Re-run at medium: 11/12, 25% cheaper.
  • Drift: kernel 7.0.0-31 → 34, Claude Code 2.1.274 → 2.1.276 mid-study.
  • Energy: RAPL is root-only → switched to the amdgpu PPT sensor on 24 Sep. Earlier runs have no energy data.
  • Memory: one OOM (22 Sep). Loading qwen3-coder alone peaked at 110 GiB → one model at a time.
Task v1 · physics in a moving container

A spinning nonagon, 13 balls, no physics library

real output · qwen3.8-t02 · clean pass, 691 s

The prompt asks for

  • Regular nonagon, radius 260 px, one turn every 7 s, clockwise
  • 13 balls, radius 14 px, numbered, spinning
  • Gravity, air friction, restitution 0.82
  • Ball–ball and ball–wall collisions with moving walls — the wall's velocity at the contact point matters

The verifier checks

  • Deterministic stepping via window.__bench.step(dt), 60 samples
  • No ball outside the polygon (1.5 px tolerance)
  • No overlapping balls (> 1 px)
  • Measured rotation period within ±10% of 7 s
Task v2 · correct physics under a pretty picture

Inner solar system + a crewed Earth → Mars → Earth mission

The prompt asks for

  • Mercury, Venus, Earth, Mars on circular orbits at correct relative radii; Mars year ≈ 1.88 Earth years
  • Launch when Mars is ≈ 44° ahead of Earth
  • Hohmann transfer ≈ 259 days, wait on Mars ≈ 455 days, mission ≈ 970 days
  • The ship must reach the planet, not a point on its orbit

The verifier checks

  • Radii & periods ±5%, Kepler's 3rd law
  • Departure window 44° ± 6°, 259 / 455 / 970 days
  • setMissionDay(d): ship position vs the planet's real position on arrival, during the wait and at return (0.35 AU tolerance)
Task v3 · follow a spec with hard constraints

"Viriato's Maze": a procedural generator with 9 constraints

real generate_maze(1) from the local model · 52.6% corridor

Constraints (all must hold for seeds 1, 7, 42, 1234)

  1. 36 rows × 28 columns
  2. Solid border (except the tunnel)
  3. Mirror symmetry: g[r][c] == g[r][27−c]
  4. No dead ends (every corridor ≥ 2 exits)
  5. One connected component
  6. Castrum: solid 6×4 block, cols 11–16, rows 15–18, ringed by corridor
  7. Exactly one wrap-around tunnel row
  8. 35–60% corridor density
  9. Deterministic per seed, different across seeds

Plus a render(grid) ASCII function. Standard library only.

Task a1 · agentic debugging (the live demo)

A recurring-task scheduler with a two-layer bug — 7 pytest tests

Layer 1 — crash

add_months(date(2026,1,31), 1) builds date(2026,2,31) → ValueError.

Layer 2 — drift

Clamping alone passes 6 of 7 tests. Chaining from the previous date loses the 31st forever: Mar 28, Apr 28…

Real fix

Anchor every occurrence to rec.start: add_months(start, i·interval). Tests are restored before scoring — editing them fails.

How we score

Clean pass, late pass, fail — and why the difference matters

Clean pass

Verifier passes and the agent returned before 3000 s. The only number we cite.

Late pass

Correct file on disk when the timeout killed the agent. A naive pass@1 counts it; we report it separately.

Checkers validated both ways

Reference solutions PASS (make check-reference, re-run 24 Sep); real broken runs FAIL with a physical reason (next slides).

29 of 50 minutes spent generating a session title

One slot. All 7,167 slot log lines are slot 0: requests queue, they don't run in parallel.

Agent request (22,494 tokens) waits; the client aborts it every ~6 min and retries.

What we got wrong — and fixed

Measurement integrity, in the open

Effort never pre-registered in practice. Claude Code defaults to effort: high; the flag was never passed. → CC_EFFORT, Claude re-run at medium.

"Thinking off" wasn't off. pi's --thinking off sends no parameter, and Ollama then reasons by default (captured). That batch proves nothing about disabling reasoning.

Energy not measured before 24 Sep: RAPL is root-only. → amdgpu PPT sensor, source recorded per sample.

Evidence overwritten. Run folders were named without the batch, so re-runs erased 6 cells' logs (CSV rows survived). → runs/<batch>/.

Late passes counted as wins. A timeout-killed run with a correct file on disk was a "pass". → clean vs late columns.

OOM and a lost night. qwen3-coder alone peaked at 110 GiB while loading; a logout killed a queue. → one model at a time, systemd units.

What the data supports — and what it doesn't

Conclusions, with their scope

Supported (measured here)

  1. Claude Opus 5: 12/12 at high, 11/12 at the pre-registered medium, 25% cheaper.
  2. Stock Qwen3.8 in Claude Code: a1 3/3, visual 0/9 (p = 0.00002) — no file written.
  3. The failure is analysis paralysis: up to 122k reasoning characters, 0 tool calls.
  4. In light harnesses the -t02 tag went 0/5 → 9/12 (p = 0.009) — but 0.2 never reached the model (Ollama /v1); the cause is open.
  5. Claude Code's default request, not its loop, blocked the local model: 1/9 → 3/3 with a lean request (p = 0.018).
  6. On a1 the local model on pi matched Claude's wall time (121 vs 136–138 s) for ~3–4 Wh of SoC energy.

Not supported

  • "Local ≈ frontier" — Claude is about 2–9× faster on visual tasks and more reliable.
  • Any ranking of pi / pi-sol / prime-agent (p ≥ 0.23).
  • SoL-Pi savings on local models — it never triggered.
  • Energy vs cloud (no cloud measurement); any payback figure (scenario only).
  • Anything beyond 4 tasks, K = 3, one model family.
